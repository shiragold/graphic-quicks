# Renderer parity: Swift vs the reference renderer

The Swift Core Graphics renderer (`Packages/PhotoAlbumKit/Sources/Rendering`) drew every
Template × Page Format of both prototype Themes, 2 × 6 × 3 = 36 renders. It used the same
stand-in photos, sample text and Matcher as the reference renderer
(`research/themes/tools/render.mjs`, previews in `research/themes/previews/`).

- `parity-kraft-scrapbook.jpg`, `parity-meadow-arch.jpg`: contact sheets. Each pair is the
  reference preview (left) and the Swift render (right), with the mean pixel difference.
- `parity-report.tsv`: one row per render, with format status, dropped Optional Slots,
  Placements and the mean absolute difference (0–1, on 96 px wide thumbnails).
- `swift/`: the Swift renders. They are regenerated by the command below and not committed.

## Reproduce

```sh
# once: stand-in photos from the reference renderer (needs research/themes/tools)
node tools/parity/export-sample-photos.mjs research/themes/tools tools/parity/photos
# every render + the contact sheets
cd Packages/PhotoAlbumKit
swift run -c release parity ../../themes ../../tools/parity/photos <research/themes/previews> ../../parity
```

## Findings (2026-10-29)

**Same structure everywhere.** All 36 renders have the same Layers in the same places,
the same masks, borders, attached decorations, palette colours and text content. The
Matcher assigns the same photo to every Slot as `render.mjs` does (36 of 36). Mean pixel
difference is 0.8 % to 4.0 % (median about 2 %). The largest values are on Kraft
Scrapbook's A4 pages, where most of the page is photo and grain.

Remaining differences, largest first:

1. **Text line breaks.** The reference estimates widths from `avgCharWidth`; Core Text
   measures real glyphs. Lines therefore break differently on some pages:
   - kraft `05-journal-entry`: the title wraps "Summer at / the Lake" instead of "Summer at
     the / Lake".
   - meadow `05-story`: the story breaks one word earlier per line.

   Sizes after fit-to-`minSize` agree within a step. This is expected and favours the Swift
   side, since what it measures is what gets printed. `maxChars` should be computed with the
   measuring renderer.
2. **Photo grain and resampling.** The stand-in photos carry `feTurbulence` grain. The
   reference rasterises them at full size inside the page. The Swift run gets 800 px JPEGs,
   decoded and drawn with Core Graphics high-quality interpolation. Fine noise differs, so
   most of the residual difference is inside photos.
3. **Shadows.** SVG `feDropShadow` and the Core Graphics shadow use different blur kernels.
   The Swift side uses blur = 2σ, with the offset mapped through the node's rotation.
   At sheet scale the shadows look the same. Their falloff was not measured separately.
4. **Text stroke weight.** Caveat (the `title` style's first choice) is not installed, so
   both sides fall back to Bradley Hand. Its only face is `BradleyHandITCTT-Bold`, and Core
   Text picks it here. The reference title still looks a little heavier; WebKit's
   antialiasing is the likely cause, not confirmed. Bundling the OFL fonts
   (`tools/fetch-fonts.mjs`) and registering them with `CTFontManagerRegisterFontsForURL`
   gives both sides the same face.
5. **Texture tile orientation.** Paper tiles are drawn with `CGContext.draw(_:in:byTiling:)`
   in a y-down space, so each tile is vertically mirrored relative to the reference. On
   noise textures this is invisible.

Nothing in the Template format needed a change to render natively. The SVG subset used by
the decoration files (paths with arcs and relative commands, basic shapes, groups with
opacity/transform, `clipPath`, and tiled `pattern` fills with `patternTransform`) is covered
by the built-in parser in `Rendering/SVGDocument.swift`. No SwiftDraw dependency is needed so
far.
